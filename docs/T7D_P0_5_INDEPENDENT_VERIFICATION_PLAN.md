## 1. 什么算“独立”

这里的“独立”指**与旧失败路径无关**，不是指换一台机器。四条同时满足才算：

1. **新账本**：用独立的网关状态目录（新的 `WORKBUDDY_DB_FILE`），旧库只读、不打开写入；
2. **新身份**：新 workspace、新 `workerKey`、新 session UUID，不复用旧 `desktop-send-b58168ae-…`；
3. **不挤容量**：预检显示容量被旧任务占着时**直接停**，不用新任务去挤（见 `verification-preflight.mjs` 的输出）；
4. **审查者不是执行者**：第 8 步必须由非本次执行者给出结论。

异机那部分（第二台物理机）仍留在 Issue #3，本方案不替代它。

## 2. 本机开工前必须知道的两件事

- 旧任务 `desktop-send-b58168ae-b46f-4116-b84c-d398f95f84f9` 仍占着唯一执行槽，**默认库上跑不了真实派工**。这属于既有状态，不是故障。
- 所以预检是硬门：`capacity_held_by_another_task` 出现时，本方案的所有后续步骤都不启动。

预检命令（只读，可在任何机器上跑）：

```powershell
cd gateway

```

输出 `ready:false` 时只会给阻塞项，不会给“试试看”的说明。

### 3.1 两条填表规则

1. **未知就写未知**：费率、档位、迟到上界这类没有证据的项，一律写“未知”并指向唯一可核实的来源（额度面板 / 目录读回），不许估。
2. **填了不等于授权**：本表由我预填是为了省你的时间；“允许执行”仍需要你在本机确认（见 §7 停止条件后的执行口令）。

### 3.2 为什么模型这一格要留读回

项目铁律是“不预选模型、不默认免费、不静默换模型”。我没有活的 WorkBuddy 桌面，读不到真实目录，所以只能写候选 + 读回要求；把猜测包装成已授权，比空着更危险。

### 3.3 预检要跑两次（都只读）

1. **首启前**：隔离网关先以“不派工”方式启动一次，让它建库；此时预检会报 `dispatch_not_enabled`，容量应为免费。
2. **派工前**：确认容量确实为空后，再设 `WORKBUDDY_DESKTOP_DISPATCH_ENABLED=1` 重启，第二次预检应 `ready: true`。

两次输出都要进证据；只留第二次属于挑好看的，不允许。

## 4. 八个步骤与证据

实现见 `gateway/src/verification-plan.ts`（`VERIFICATION_STEPS`）。每步都自带“这条证据不能证明什么”，代码里 `mayNotProve` 不允许为空。

| # | 步骤 | 需要的证据 | 只能证明 | 不能证明 |
|---|---|---|---|---|
| 1 | 预检 | capacity / dispatch_flag / database_path / workspace | 本次用的目录与容量状态 | 容量空≠旧任务无副作用 |
| 2 | 预留身份 | reserved_session / worker_key | 预留的是哪个 UUID | 预留≠已创建 |
| 3 | 原生创建 | create_result / elapsed_ms | 这一次返回了什么 | 超时/报错≠未到达 |
| 4 | 桌面登记 | registered_at | 某一刻登记了 | 没登记≠没创建 |
| 5 | 派工 | request_id / receipt_state / lease | 发出过哪个请求、当时回执 | 无回执≠无副作用 |
| 6 | 收到报告 | report_text / received_at | 收到了某段文本 | 收到≠原生停止≠验收 |
| 7 | 原生停止 | stop_evidence | 某一刻呈停止状态 | 停止≠结果正确 |
| 8 | 独立审查 | reviewer / reviewed_artifact / review_conclusion | 谁在什么材料上给了结论 | 审查≠真实派工验收 |

## 5. 允许的结论句式

`allowedClaims()` 由“哪几步记到了”机械推导，没证据就不出句子：

- 只有 1 记到 → “本次验证在独立状态目录中开始，旧账本未被打开写入。”
- 2+3 记到 → “本次预留身份与原生返回身份一致。”
- 5 记到 → “网关记录到一次派工请求及其回执。”
- 6 记到、7 没记到 → “已收到报告，但原生停止尚未确认。”
- 6+7 记到 → “已收到报告，且记录到原生停止证据。”
- 8 记到 → “存在一份由非执行者给出的审查结论。”

每条都带一句限制说明，不允许单独引用前半句。

## 6. 证据怎么存

- 一笔验证一个 JSON：`<STATE_DIR>\verification\<timestamp>-evidence.json`，内容为 `VerificationEvidence[]`（`stepId / kind / value / observedAt`）。
- 空字符串不算证据（`verification-plan.ts` 已实现），防止“点了但没写”。
- 汇总用 `verificationSummary(evidence)` 得到 `recorded / missing` 计数；**没有 pass/fail 字段**，这是刻意设计。

## 7. 停止条件与回滚

出现下列任一，立即停手，保留现场，不重试：

1. 第 3 步超时或报错（不确定），且第 4 步 5 分钟内无登记；
2. 第 5 步回执为 `outcome_unknown`，或租约结算为 `abandoned`（**2026-11-02 run7 实际触发过：宁可停，也不重派**，见 §10）；
3. 第 6 步收到报告但第 7 步 10 分钟内无停止证据；
4. 任何一步出现身份或工作区不符。

回滚只做三件事：关掉临时网关进程、把 `<STATE_DIR>` 整个挪走存档、原样保留证据 JSON。**不改旧库、不删探针日志、不改 `workers.state`。**

## 8. 与验收门槛的关系

本方案能补的是“有据可查的一次真实执行证据”。它**不**替代：

- V01–V15 里的真机项与第二台物理机（Issue #3）；
- 前端项（Issue #6）；
- 许可证定稿；
- 旧任务的裁决（已单独成文）。

## 9. 边界

- 预检通过≠派工会成功；脚本只回答“能不能开始记录”。
- 本方案不产生任何 `outcome_unknown` 的自动处置：不确定就留着，等人核对。
- 异机不可用期间的结论，一律要写明“单机隔离账本”，不得表述为跨机验证。
